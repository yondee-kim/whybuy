# WHYBUY 데이터 설계

Version 1.0

---

# 이 문서를 쓰는 이유

WHYBUY는 구매 금액도, 상품명도, 검색어도 수집하지 않는다.

이 방침은 유지한다.

브랜드 약속이자 규제 대응 자산이다.

---

그런데 그 결정에는 대가가 있다.

수집을 최소화하면

**이 서비스가 실제로 효과가 있는지 증명할 방법도 함께 사라진다.**

---

편이가 나타났을 때

사람들이 실제로 멈추는지,

어떤 상황에서 더 잘 멈추는지

아무도 모르게 된다.

---

그래서 하나만 남긴다.

**개입 이벤트와 그 결과.**

개인을 식별하지 않으면서

개입이 작동하는지 측정할 수 있는 최소한의 기록이다.

---

# 시점이 중요하다

이 설계는 **출시 전에 확정해야 한다.**

나중에 필드를 추가하면

그 이전 기록에는 값이 없다.

---

특히 "편이를 보고 몇 초 만에 반응했는가"는

지금 저장하지 않으면

영원히 복원할 수 없다.

---

# 원칙

## 1. 개인을 식별하지 않는다

기기 단위 익명 해시만 사용한다.

역추적이 불가능하도록 설계한다.

---

## 2. 앱 이름 대신 카테고리

`com.coupang.mobile`이 아니라

`SHOPPING`으로 기록한다.

---

로컬 DB에는 앱 이름을 저장한다.

사용자가 자기 기록을 보려면 필요하기 때문이다.

집계나 외부 전송 시에는 카테고리만 쓴다.

---

## 3. 문장을 저장하지 않는다

감정은 코드로만 남긴다.

`TIRED`이지 "오늘 회의 때문에 힘들었어요"가 아니다.

---

기타 입력(최대 20자)은

기기에만 저장하고

집계 대상에서 제외한다.

---

## 4. 기본은 로컬

모든 기록은 기기에 남는다.

서버 전송은 사용자가 켤 때만 이루어진다.

---

# 스키마

## encounter_log 확장

기존 필드에 아래를 추가한다.

| 필드 | 타입 | 설명 |
|---|---|---|
| appCategory | TEXT | SHOPPING / DELIVERY / GAME / FINANCE / SNS / ETC |
| dismissLatencyMs | INTEGER | 노출부터 첫 반응까지 |
| flowCompleted | INTEGER | 3단계 완주 여부 |
| dayOfWeek | INTEGER | 1(월) ~ 7(일), 새벽 4시 기준 |
| hourOfDay | INTEGER | 0 ~ 23 |
| ruleFrequency | TEXT | 당시 적용된 빈도 규칙 |

---

## 전체 구조

```kotlin
@Entity(
    tableName = "encounter_log",
    indices = [
        Index("serviceDate"),
        Index("packageName", "shownAt"),
        Index("appCategory")
    ]
)
data class EncounterLogEntity(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,

    // 대상
    val packageName: String,
    val appName: String,
    val appCategory: String,

    // 시각
    val shownAt: Long,
    val serviceDate: String,
    val dayOfWeek: Int,
    val hourOfDay: Int,

    // 사용자 선택
    val emotionCode: String?,
    val emotionMemo: String?,
    val decisionCode: String?,

    // 반응
    val endReason: String,
    val dismissLatencyMs: Long,
    val durationMs: Long,
    val flowCompleted: Boolean,

    // 당시 규칙
    val ruleFrequency: String,

    val createdAt: Long = System.currentTimeMillis()
)
```

---

## 각 필드를 남기는 이유

### appCategory

지금은 쇼핑만 다룬다.

나중에 배달, 게임, 금융으로 넓힐 때

스키마를 바꾸지 않아도 된다.

---

카테고리별로 개입 효과가 다를 것이다.

배달앱의 밤 11시와

쇼핑앱의 점심시간은

같은 행동이 아니다.

---

### dismissLatencyMs

편이가 나타나고

사용자가 처음 무언가를 누르기까지의 시간.

---

이 값이 짧으면

사용자가 생각하지 않고 치운 것이다.

길면

실제로 멈춘 것이다.

---

WHYBUY가 "몇 초를 만든다"고 말하는 이상

그 몇 초를 측정할 수 있어야 한다.

---

### flowCompleted

3단계를 끝까지 갔는지.

---

중간 이탈이 많다면

플로우가 길거나 부담스러운 것이다.

---

### dayOfWeek / hourOfDay

shownAt에서 계산할 수 있지만

따로 저장한다.

---

집계 쿼리가 단순해지고

시간대별 분석이 쉬워진다.

---

새벽 4시 기준으로 계산한다.

새벽 2시의 쇼핑은 전날이다.

---

### ruleFrequency

당시 적용된 규칙.

---

규칙과 결과의 관계를 보기 위해서다.

매번 나오게 설정한 사용자와

하루 한 번인 사용자의

보류율이 다른지 알 수 있다.

---

# 감정 분류축

## 문제

지금 감정 선택지는 자연스러운 문구다.

그건 좋다.

사용자에게는 그렇게 보여야 한다.

---

하지만 데이터로 보면

`TIRED`와 `REWARD`가 어떻게 다른지

기계는 모른다.

---

## 해결

각 감정에 두 개의 축을 부여한다.

---

```kotlin
enum class Emotion(
    val label: String,
    val valence: Int,   // -1 부정 / 0 중립 / 1 긍정
    val arousal: Int    // 0 낮음 / 1 높음
) {
    TIRED("조금 지쳤어요.", -1, 0),
    BROWSING("그냥 구경 중이에요.", 0, 0),
    REWARD("나에게 선물하고 싶어요.", 1, 1),
    NEEDED("정말 필요한 것 같아요.", 0, 0),
    UNKNOWN("잘 모르겠어요.", 0, 0)
}
```

---

## valence-arousal이란

감정 연구에서 오래 쓰인 2축 모델이다.

- valence: 좋은 감정인가 나쁜 감정인가
- arousal: 각성도가 높은가 낮은가

---

지친 상태는 부정적이지만 각성도가 낮다.

보상 심리는 긍정적이면서 각성도가 높다.

이 둘은 소비에서 전혀 다르게 작동한다.

---

## 왜 지금 넣는가

두 칸 추가하는 데 10분이면 된다.

나중에 넣으면

과거 기록에는 값이 없다.

---

## 주의

이 값을 사용자에게 보여주지 않는다.

---

"당신은 부정적 감정 상태입니다"

이건 WHYBUY가 절대 하지 않는 말이다.

---

분류축은 내부 분석용이다.

화면에는 문구만 나온다.

---

## 확장 시

선택지는 5~7개를 넘기지 않는다.

너무 많으면

한 항목당 표본이 부족해진다.

---

문구는 바꿔도 된다.

코드값은 절대 바꾸지 않는다.

---

# 핵심 지표

## 개입 후 보류율

```
보류율 = (THINK_MORE + LATER) / 전체 노출
```

---

이 숫자 하나가

WHYBUY가 작동하는지 아닌지를 말해준다.

---

## 세부 지표

| 지표 | 계산 | 의미 |
|---|---|---|
| 완주율 | flowCompleted / 노출 | 플로우 부담 정도 |
| 즉시 이탈률 | latency < 1500ms 비율 | 편이가 무시당하는 비율 |
| 평균 체류 | durationMs 평균 | 실제로 멈춘 시간 |
| 감정별 보류율 | 감정 코드별 분리 | 어떤 상태에서 효과적인가 |
| 시간대별 보류율 | hourOfDay별 분리 | 언제 개입이 유효한가 |
| 규칙별 보류율 | ruleFrequency별 분리 | 빈도와 효과의 관계 |

---

## 앱 삭제와의 관계

가장 중요한 관계는 이것이다.

---

노출 빈도가 높을수록

삭제가 빨라지는가.

---

만약 그렇다면

기본 규칙을 더 조용하게 바꿔야 한다.

---

이건 로컬 데이터만으로는 알 수 없다.

Play Console 삭제 지표와

앱 내 노출 빈도를 함께 봐야 한다.

---

# 집계와 전송

## MVP

전송하지 않는다.

모든 기록은 기기에만 있다.

---

## 이후

사용자가 동의하면

집계된 값만 보낸다.

---

### 보내는 것

```json
{
  "anonId": "기기 단위 해시",
  "period": "2026-08",
  "aggregates": [
    {
      "category": "SHOPPING",
      "hourBucket": "22-24",
      "emotionCode": "TIRED",
      "shown": 12,
      "held": 8,
      "avgLatencyMs": 3400
    }
  ]
}
```

---

### 보내지 않는 것

- 개별 이벤트
- 앱 패키지명
- 기타 입력 문장
- 정확한 시각
- 기기 식별자 원문

---

## anonId 생성

```
SHA-256(설치 시 생성한 랜덤 UUID)
```

---

기기 ID나 광고 ID를 쓰지 않는다.

앱을 지우면 값이 사라진다.

재설치하면 다른 사람이 된다.

---

이건 결함이 아니라 의도다.

---

# 개인정보 관점

## 수집하지 않는 것을 증명한다

"수집하지 않습니다"라고 말하는 것과

증명하는 것은 다르다.

---

출시 전에 아래를 문서화한다.

- 데이터 흐름도
- 각 필드의 수집 목적과 보관 기간
- 서버로 나가지 않는 항목 목록
- 삭제 절차

---

이 문서는

Play Console 데이터 안전 섹션 작성에 그대로 쓰인다.

---

나중에 다른 조직과 이야기할 일이 생기면

이 문서가 협상 시간을 줄여준다.

다만 그건 부수 효과이지

지금 그것 때문에 만드는 것은 아니다.

---

# 카테고리 정의

| 코드 | 대상 | MVP |
|---|---|---|
| SHOPPING | 쿠팡, 무신사, 지그재그, 올리브영 | O |
| DELIVERY | 배달의민족, 쿠팡이츠, 요기요 | O |
| SNS | 인스타그램, 틱톡 | X |
| GAME | 과금 화면 | X |
| FINANCE | 증권, 코인 | X |
| ETC | 그 외 | O |

---

MVP는 SHOPPING과 DELIVERY만 다룬다.

나머지는 스키마에만 존재한다.

---

이렇게 해두면

나중에 대상을 넓힐 때

DB를 건드리지 않아도 된다.

---

# 대화 플로우 추상화

## 현재

플로우가 `OverlayController`에 하드코딩되어 있다.

---

## 목표

카테고리별로 문구와 선택지를 바꿀 수 있어야 한다.

---

배달앱에서

"나에게 선물하고 싶어요"는 어색하다.

"오늘은 좀 쉬고 싶었어요"가 맞다.

---

## 구조

```kotlin
interface FlowProvider {
    fun greeting(category: String): String
    fun emotions(category: String): List<Emotion>
    fun decisions(category: String): List<Decision>
}
```

---

MVP에서는 단일 구현으로 충분하다.

다만 인터페이스로 분리해 두면

나중에 확장할 때 구조를 안 바꿔도 된다.

---

# 하지 않는 것

## 문장 수집

기타 입력을 서버로 보내지 않는다.

한 번 열어두면

그 안에 무엇이 들어올지 통제할 수 없다.

---

## 화면 내용 접근

접근성 서비스로 화면을 읽지 않는다.

기술적으로 가능해도 하지 않는다.

---

## 광고 식별자

ADID를 사용하지 않는다.

---

## 실시간 전송

이벤트가 발생할 때마다 서버로 보내지 않는다.

집계 후 주기적으로만 보낸다.

---

# 정리

WHYBUY가 남기는 것은

무엇을 샀는지가 아니라

그 순간 어떤 마음이었는지

사용자가 스스로 고른 단어 하나다.

---

그리고

그 뒤에 잠시 멈췄는지.

---

그것만으로

이 서비스가 작동하는지 알 수 있다.

그 이상은 필요 없다.
