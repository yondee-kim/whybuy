# WHYBUY 개선 필요 사항

작성일: 2026.07.24
평가 관점: M&A / 사업 가치 관점

---

## 0. 현재 진단 요약

| 항목 | 상태 | 판단 |
|---|---|---|
| 매출 | 없음 | 구조적 부재 (철학에 내장) |
| 사용자 | 없음 | 미출시 |
| 기술 자산 | 오버레이 + 앱 감지 + 로컬 DB | 진입장벽 없음 (2~4주 재현 가능) |
| 문서 | 기획 16종 | 인수 대상 아님 |
| 현 시점 인수 가치 | 사실상 0 | pre-launch 전 제품 공통 |

**핵심 문제는 아이디어가 아니라, 가치를 측정할 숫자가 하나도 없다는 점.**

---

## 1. 최우선 — Play Store 심사 통과 검증

**다른 모든 항목에 선행한다. 여기서 막히면 나머지는 전부 무의미하다.**

### 리스크
- 오버레이(`SYSTEM_ALERT_WINDOW`) + 앱 실행 감지 조합은 Google Play 정책상 반려 위험이 높다.
- 특히 **접근성 권한(AccessibilityService) 기반이면 반려 가능성이 매우 높다.** Google은 접근성 권한을 장애인 보조 목적 외 사용에 대해 지속적으로 제재해왔다.
- 정책 변경 한 번에 제품 전체가 동작 불능이 될 수 있다. 인수 실사에서 반드시 걸리는 항목.
- iOS 확장이 사실상 불가능 — TAM(전체 시장) 자체가 절반으로 제한된다.

### 해야 할 일
- [ ] 접근성 권한 대신 `UsageStatsManager` + `SYSTEM_ALERT_WINDOW` 조합으로 구현 가능한지 검증
- [ ] 최소 기능만 담은 빌드로 **실제 심사를 한 번 받아본다** (내부 테스트 트랙 아님, 프로덕션 심사)
- [ ] 반려 시 사유를 문서화 — 이것 자체가 나중에 실사 대응 자료가 된다
- [ ] 정책 변경 시 대체 동작(fallback) 시나리오 1개 준비

## 2. 개입 이벤트 로그 스키마 설계

**나중에 붙이면 과거 데이터가 없다. 출시 전에 반드시 확정해야 한다.**

### 원칙
구매 금액·상품 정보 미수집 방침은 **유지한다.** 이것은 규제 대응 자산이다.
다만 **개입 이벤트와 그 결과는 익명 로그로 반드시 남긴다.** 이게 유일한 자산이다.

### 최소 스키마 (예시)

| 필드 | 설명 | 개인정보 해당 |
|---|---|---|
| `event_id` | 개입 이벤트 고유 ID | 아니오 |
| `anon_user_id` | 기기 단위 익명 해시 | 아니오 (재식별 불가 설계) |
| `app_category` | 앱 분류 (커머스/배달/게임) — 앱명 아님 | 아니오 |
| `triggered_at` | 노출 시각 (요일·시간대) | 아니오 |
| `emotion_code` | 사용자가 고른 감정 (코드값) | 아니오 |
| `flow_completed` | 3단계 대화 완주 여부 | 아니오 |
| `outcome` | 진행 / 보류 / 이탈 | 아니오 |
| `dismiss_latency_ms` | 노출~반응 소요 시간 | 아니오 |

### 도출해야 할 핵심 지표
- **개입 후 보류율** = 보류 / 전체 노출 — 이 숫자 하나가 사업의 전부다
- 감정별·시간대별·카테고리별 보류율 차이
- 노출 빈도와 앱 삭제율의 상관관계

## 3. 감정 선택지를 연구 가능한 분류 체계로 재설계

### 문제
현재 감정 선택지가 임의 문구라면, 쌓인 데이터가 학술적·상업적으로 쓸모없어진다.

### 해야 할 일
- [ ] 감정 선택지를 기존 심리학 척도에 **매핑 가능한 형태**로 재설계
  - 참고: 충동구매 경향 척도(Impulse Buying Tendency Scale), 감정소비 관련 기존 연구 분류
- [ ] 각 선택지에 고정 코드값 부여 — 문구는 바뀌어도 코드는 불변
- [ ] 선택지 개수는 5~7개 이내 (통계적 유의성 확보 가능한 수준)

### 왜 필요한가
연구기관·대학과 연결되면 **"검증된 개입"이라는 근거**가 생긴다.
B2B 영업에서 인수자가 사는 건 앱이 아니라 이 근거다.

## 4. 제품 정체성 재정의 — 리텐션 구조 문제 해결

### 문제
**성공이 곧 이탈로 직결되는 구조.**
사용자가 충동구매 습관을 고치면 앱을 지운다. 삭제율을 핵심 지표로 본 판단은 정확하지만, 그 지표가 좋아도 LTV(고객 생애 가치)는 나오지 않는다. M&A 밸류에이션은 LTV 없이 계산되지 않는다.

### 해결 방향
정체성을 **"충동구매 억제 앱" → "충동 행동 개입 레이어"** 로 확장한다.

동일 기술이 그대로 적용되는 영역:
- 도박·베팅 앱
- 게임 과금 (특히 확률형 아이템)
- 배달 앱 (심야)
- 주식·코인 앱 (충동 매매)

사용자는 **대상만 바꿔가며 남는다.** 인수자 입장에서 시장 크기가 완전히 달라진다.

### 해야 할 일
- [ ] 앱 카테고리 분류 체계를 커머스 외 영역까지 확장 가능하게 설계
- [ ] 대화 플로우를 카테고리별로 분기 가능한 구조로 추상화 (하드코딩 금지)

## 5. 수익 모델 재설계

### 문제
구매 금액·상품 정보 미수집 결정은 사용자 신뢰에는 좋지만, 표준적 수익화 경로를 **스스로 전부 차단**한다.
- 커머스 제휴 — 불가
- 리타게팅 광고 — 불가
- 데이터 판매 — 불가

남는 건 구독뿐인데, **"소비를 줄이려는 사람에게 월 구독료를 받는다"** 는 설득이 매우 어려운 판매다.

### 대안 — B2B2C SDK

앱을 파는 게 아니라 **"결제 직전 개입 엔진"** 을 판다.

**타깃 고객**
- 카드사 / 저축은행 / 핀테크 — 금융위 소비자보호 평가 지표 대응 필요
- 도박·중독 관련 공공기관 및 상담 기관
- 게임사 (자율규제 대응)

이들은 앱을 사는 게 아니라 **자기 앱에 붙일 모듈**을 원한다.

### 해야 할 일
- [ ] 핵심 로직을 앱과 분리해 SDK화 가능한 구조로 설계
- [ ] **개인정보 미수집 설계를 문서화된 자산으로 만든다**
  - 개인정보 영향평가(PIA) 대응 문서
  - 데이터 흐름도 (수집하지 않는다는 것의 기술적 증명)
  - 이 문서가 있으면 금융사 실사에서 수개월을 절약해준다. 이게 실제 협상력이다.

## 7. 하지 말아야 할 것

- **기획 문서를 더 쓰는 것.** 16종은 이미 충분하다. 문서는 가치를 만들지 않는다.
- **기능을 더 붙이는 것.** 출시 전 기능 추가는 심사 리스크만 키운다.
- **다운로드 수를 목표로 잡는 것.** 인수자는 다운로드를 보지 않는다.
- **지표 없이 투자·인수 논의를 시작하는 것.** 협상력이 0인 상태로 테이블에 앉는 것.

---

## 8. 대화 가능 시점

M&A 논의가 실질적으로 가능해지는 최소 조건:

- 출시 후 6개월 경과
- 활성 사용자 10,000명 이상
- **개입 후 보류율이 통계적으로 유의미한 수준으로 측정됨**
- Play Store 정책 리스크 해소 증명

그 전까지는 M&A 단계가 아니라 **제품-시장 적합성(PMF) 검증 단계**다.
